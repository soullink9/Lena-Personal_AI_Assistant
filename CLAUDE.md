# Working on Lena

Instructions for AI coding assistants working in this repository. The same rules for people are in [CONTRIBUTING.md](CONTRIBUTING.md); read it, [ARCHITECTURE.md](ARCHITECTURE.md) and [docs/development/Development.md](docs/development/Development.md) before changing anything.

## Rules

- **Versions move together.** The app (`versionName` in `android/app/build.gradle.kts`), the integration's `manifest.json`, the `version:` line of both Open WebUI files, the voice bridge's `LenaVoiceBridge/` User-Agent and the newest `CHANGELOG.md` section always carry the same version. `versionCode` goes up by one per release. Versions are plain numbers (`0.6.3`), with no "beta" or other suffix.
- **Every changelog section ends with what to update.** The last thing in each release's section is a `### What to update` list with one line per part, each saying `Need to update` or `No update needed (oldest working vX.Y.Z)`, in this order: `Modelfile`, `Lena HA Integration`, `Lena Android App`, `Open WebUI Tools`, `Open WebUI Filters`, `Voice Bridge`. The oldest working version is the last release whose list said `Need to update` for that part (copy it from the previous release's line when this one doesn't change the part), so people can tell whether their copy, above all the hand-updated Modelfile and Open WebUI files, is new enough without reading every release. `tools/check.py` fails while the newest section lacks a line or any section names a version that isn't the last one that needed the part.
- **No 1.0.** Stay on 0.x until the owner explicitly says otherwise.
- **Consistent naming.** Use the names already used for the same thing; one concept, one name, in code, settings, UI text and docs.
- **Documentation sync.** Whenever a function, class or logic block changes, update its comment, the docs that describe it and the changelog in the same commit. Comments explain why.
- **Readability over cleverness.** No dense one-liners or clever shortcuts.
- **Test integrity.** Keep existing behavior. Run `python3 tools/check.py` (it also runs `tests/release/test_release.py`); every job of `.gitea/workflows/test.yml` (the Home Assistant tests, the app's checks and build) must pass.
- **Gitea first.** The project lives on Gitea (`.gitea/workflows/`), which push-mirrors to GitHub, the public copy. Gitea's workflows use no `uses:` actions and nothing from GitHub, so they work when GitHub is down, and run their steps in bash (`defaults: run: shell: bash`; Gitea's runner would use sh); shared steps live in `scripts/` (plain shell, and Python with its standard library only), used by both Gitea's and GitHub's workflows. Public links (README, docs, release notes) point at GitHub. Releasing is in CONTRIBUTING.md.
- **Conventional Commits** for every commit (`feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `build:`, `ci:`, `chore:`, `perf:`, with an optional scope).
- **Commits are the owner's.** Author and commit every change as `Soullink <344372660+soullink9@users.noreply.github.com>`, with no AI co-author, session or "generated with" lines in commit messages or pull requests.
- **Default settings first.** Before every build and release, check `adjustments/defaults.env` (see its README) for values typed after a setting's `=`, review them, and run `python3 tools/defaults.py apply`, which writes them into `Defaults.kt`, moves them to its **Current default** comment and empties the value. Never edit `Defaults.kt` by hand. A new setting with a default gets an entry (add it to `SETTINGS` in `tools/defaults.py`, then apply). `tools/check.py` fails while a change is waiting, and the release workflow won't publish.
- **No new dependencies** (Gradle libraries or plugins, Python packages) without the owner's explicit approval. `tools/check.py` enforces the approved list.

## Standing constraints

- Android: `targetSdk` stays at 36 until the owner's phone runs a newer Android. `compileSdk` is 37 (the owner's choice, 2026-11-25), so the newest Jetpack libraries build; it only sets which APIs the build sees. `minSdk` is 35 (Android 15), the owner's minimum for phones, tablets and Android TV alike. No code for older Android: no `Build.VERSION` checks, compat shims, `-v31`-style resource folders or deprecated fallbacks for anything Android 15 has; use the platform API where AndroidX only wraps it for older versions. Anything newer than Android 15 goes behind a version check, and the build's lint fails on any call that isn't (NewApi is fatal).
- Home Assistant: everything is set up in the UI; nothing in YAML.
- Home Assistant: latest release only. The integration targets the newest Home Assistant release the owner runs (now 2026.11: `hacs.json`'s `homeassistant`, and the last release in the workflows' test matrix, which `tools/check.py` keeps equal) and nothing older. No backwards compatibility: no shims, `getattr`/`hasattr`/`ImportError` fallbacks or version checks for older Home Assistant, and no tests for it. Use the current API as Home Assistant documents it (https://contributors.home-assistant.io/blog); when a new release changes one, move to the new way and drop the old. When the owner moves to a newer release, raise the minimum to it in the same change. Before building something, check whether that Home Assistant release already does it, and use that instead of building it again.
- Home Assistant Marketplace: Lena is installed from the Marketplace (Settings → Marketplace, built into Home Assistant since 2026.11; HACS before). Keep what it needs: `hacs.json`, the manifest's keys and `categories` (`ai_voice.voice_assistants`), and the brand images in `custom_components/lena/brand/`. `tools/check.py` checks them.
- No downloads at build time beyond Gradle's own (models and the C reference are committed).
- Never commit secrets, tokens, signing keys or personal data. Never ask anyone to paste tokens into a chat.
- Public README: short, with the Disclosure section at the top; details live in `docs/`.
